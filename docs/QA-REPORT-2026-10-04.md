### QA-001 A declined-then-retried or late card payment leaves the order paid but cancelled, with its stock released
Severity: **P2 (re-test)**. It was P0 as first observed. **Possibly in-progress.**
Observed: 2026-10-04 ~21:05 UTC, before 039/040. Re-tested: 2026-10-05 09:42 UTC.
Re-test result: The live `mark_order_paid` (040) now locks the row and, for a cancelled, expired or payment-failed order, sets `checkout_state='paid_needs_review'` and `hold_reason='paid_after_cancellation'` instead of `paid`. The rolled-back repro now gives `decline then retry: status=cancelled state=paid_needs_review paid=t fulfil=cancelled hold=paid_after_cancellation`. The silent loss is now a staff-visible hold. What remains:
- `release_checkout_order` still doesn't cancel the PaymentIntent, so a released order can still be charged or authorized.
- `readyToFulfil` (`src/lib/backend/shipstation.ts:53`) uses `paid`, so a held order is still exported to ShipStation, as `cancelled`.
- The hold depends on someone acting on it (see QA-002: the new `payment-safety-15min` job is also a no-op).

The original record follows.
Area: 4.3
Where: `public.mark_order_paid`, `public.release_checkout_order` (migration 010), `supabase/functions/stripe-webhook/index.ts:202-215`, `src/components/stripe-payment.tsx:30-48`
Steps:
1. A card order is in `payment_pending` with stock reserved.
2. The order is released. Either the first card is declined (the webhook gets `payment_intent.payment_failed` and calls `release_checkout_order(..,'payment_failed')`), or the 30-minute expiry runs (`'expired'`). The order becomes `status=cancelled`, `fulfillment_status=cancelled`, and its reservations are released.
3. The same PaymentIntent then succeeds. Stripe allows a retry on the same intent, and `StripePayment` keeps the Pay button enabled after an error. The webhook then calls `mark_order_paid`.

Expected: Money is never captured for an order we have cancelled. Either the PaymentIntent is cancelled when the order is released, or `mark_order_paid` refuses or flags an order that is no longer pending, and the payment is refunded or reviewed.

Actual: `mark_order_paid` unconditionally sets `paid=true, checkout_state='paid'`. `status` and `fulfillment_status` stay `cancelled`, and the stock is already released. `release_checkout_order` never cancels the PaymentIntent. ShipStation then exports the order as `cancelled` (`toExportOrder` maps status cancelled → cancelled). The customer has paid, nothing ships, and nobody is alerted.

Evidence: rolled-back block, run twice with identical results:
```
after expiry: status=cancelled state=expired paid=f
after late payment: status=cancelled state=paid paid=t fulfil=cancelled
replayed event payments=1
```
```
late payment: status=cancelled state=paid paid=t fulfil=cancelled
```
Env: live schema, rolled back. The full Stripe round trip was not run because there are no Stripe test keys. The decline-then-retry path is established from the code.
Suggested fix: Cancel the PaymentIntent inside the release path (and treat a cancel failure as "already paid"). Make `mark_order_paid` lock the row and, if the order is not `payment_pending`/`checkout_started`, record the payment but flag the order for refund or staff review instead of marking it paid.

### QA-006 The post-login open redirect bypasses the check with a control character in `next`
Severity: P1
Area: 4.9, 4.20
Where: `src/lib/safe-redirect.ts:17-22`, used by `src/lib/backend/auth-actions.ts:62,86` and `src/app/portal/login/page.tsx:43-46`. `allowedNext` (`src/lib/access-state.ts:119-127`) passes unknown paths through.
Steps:
1. `safeNextPath("/\t/evil.example", "")` (also `\n`, `\r`).
2. Resolve the result as a URL.

Expected: Same-site path or fallback.

Actual: Returns `"/\t/evil.example"`. Browsers strip tab and newline characters from URLs, so it resolves to `https://evil.example/`. A link such as `/portal/login?next=/%09/evil.example` sends a freshly signed-in user off-site.
Evidence (run twice):
```
"/\t/evil.example" -> "/\t/evil.example" resolves to https://evil.example/
"/\n/evil.example" -> ... resolves to https://evil.example/
```
`/auth/callback` is **not** affected, because its `ALLOWED_NEXT` allow-list catches it. The listed `https://`, `//` and `/\` payloads are correctly rejected.
Env: unit-level (tsx). End-to-end needs a test account; creating auth users was out of scope.
Suggested fix: Reject any `next` containing characters below 0x20 or a backslash anywhere. Better, parse with `new URL(next, origin)` and require `url.origin === origin`, then redirect to `url.pathname + url.search`.
